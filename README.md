# Keel

> **keel** /kiːl/ n. 龙骨——船体最底部的中轴结构。它不提供动力，只决定船在浪里翻不翻。

**一个用来回答「harness 层的改动到底有没有用」的 Agent 运行时与配套评测链路。**

公开榜单测的是模型能力：换个模型，分数会动；而给 harness 加一层护栏、换一种切片策略、调整预算分配，分数很可能一分不掉——因为它根本不测「过程有多浪费」。于是 harness 层的工程决策长期缺少判据，只能靠感觉做。

这里的做法是把每个机制都做成**可开关**的，然后在**确定性执行**下做 A/B 对照：用规则驱动的离线 Provider 顶替真实模型，消除模型方差，使两组之间的差异可以完全归因到 harness 改动本身，而不是模型这次心情好。六组消融的结果由 CI 自动生成、回填进本文、并在每个 PR 上与基线逐项比对，指标退化即阻断合并。

**被测对象**是一个完整的 Agent 运行时：上下文工程（分层切片 / Token 预算调度 / 压缩）· 四层记忆系统（混合检索 / 遗忘曲线 / 反思固化）· Loop Engineering（护栏 / 死循环检测 / 熔断 / 反思重规划）· 多 Agent 编排（DAG 分层并发 / Planner-Worker-Critic）· 工具沙箱（AST 白名单 / 目录穿越防护）。

> 默认跑在**离线 Mock Provider** 上：不需要任何 API Key，`pip install` 完就能跑通全部功能、114 个测试和整套消融实验。配一个 Key 即可无缝切换到 DeepSeek / OpenAI / 通义千问。

### 怎么读这些数字

**护栏的第一要求是不误杀。** 正常任务两组应当逐项完全一致，这一行和病态任务上那些百分比同样重要——一个把正常任务也砍掉的护栏毫无价值。病态任务上护栏把步数和 token 砍掉大半，且被中止后仍产出降级答案而不是抛错。

**真实模型复跑**（DeepSeek，8 个正常任务）：两组均 0 次护栏触发、8/8 有答案、4/4 答对，token 差异 +4.5% 落在模型自身方差内。**病态任务的量化必须在 mock 下做**——它靠 Mock 的确定性触发词复现，真实模型不会听这个词，这是本 bench 的局限而不是特性。

**MMR 那组被系统性低估。** Mock 用的 hashing 向量是词袋随机投影，不懂近义词，改写句之间余弦本来就不高，MMR 能压的空间因此变小。所以 bench 同时报了一个完全不依赖 embedding 的词重合度指标，那一列更可信。

**DAG 编排有三点和直觉相反的结论：**

1. **加速比在 mock 和真实模型下基本相同**（mock 约 1.5×，真实模型三轮 1.35 / 1.48 / 1.80×）。我原本推测"真模型延迟大所以加速比更高"，**这是错的**——加速比是个比值，延迟等比放大会在分子分母上一起放大然后抵消。真正的上界是图的结构（关键路径长度），不是延迟。
2. 但端到端墙钟 DAG 反而**更慢**，token 贵好几倍：多了规划、汇总、质检三次调用，每个 worker 还各自跑一遍完整 ReAct、各带一份完整上下文。
3. 所以真正的结论是：**这个规模的任务不该编排**。编排要等到子任务本身足够重、数量够多才回本。这正是 Orchestrator 对单节点任务自动降级直跑的理由——而且从数据看，这个降级阈值还可以再往上调。

**动作清单那组要看 scratchpad 列。** `verbatim` 说明没被压缩，两组自然一样；一旦变成 `middle_out` / `drop_zone`，关闭组就开始重复调用——这精确划出了"关键状态必须放进不可丢弃分区"这个设计的作用域。

### 写 bench 抓出来的四个 bug

评测本身的最大收益不是那些百分比，而是它逼着每个开关都被真的拨动一次：

1. **`cycle_detect_window=0` 关不掉周期检测。** `fps[-0:]` 在 Python 里等价于 `fps[0:]`，取的是**全部**历史。想关掉检测器的人会得到一个反而更激进的无限窗口检测器——这种"看着关了其实开着"的开关会让消融结论直接反过来。
2. **编排模式的 token 少记了 80% 以上。** `Worker` 调 `engine.run()` 时没把 tracer 传下去，引擎自建了一条新 trace，子任务的全部 LLM 消耗漏出编排的账本。修复后 DAG 组的 token 从 6075 变成真实的 33839——成本核算错到这个程度就没法回答"钱花在哪"了。
3. **测试套件不是密闭的。** `.env` 一改成真实 provider，没有显式注入 provider 的用例就偷偷去打网络请求：套件耗时从 22s 涨到 157s，断言结果取决于当天模型的心情。测试的确定性不能依赖一个配置文件，现在 conftest 把全局 Provider 钉死在 Mock 上。
4. **embedding 降级既没记性也不出声。** DeepSeek 只提供 chat，`/embeddings` 恒定 404，而降级逻辑每次都要白跑 3 次 HTTP 重试加指数退避才 fallback。更危险的是它**完全静默**：hashing 向量不懂近义词，且一旦维度和库里已有向量不一致，`cosine()` 遇到长度不等会**直接返回 0.0 而不报错**，向量通道静默失效、检索悄悄退化成纯 BM25，全程零异常。现在降级会 latch、会告警、会写进 trace 属性。

## 一、上下文工程 `keel/context/`

### 分层切片：五种策略，可直接对比

| 策略 | 做法 | 适用 |
|---|---|---|
| `fixed` | 定长 + 重叠 | 基线，用于对照 |
| `recursive` | 按分隔符优先级递归下切 | 通用默认值 |
| `structure` | Markdown 感知：**标题路径下推**、代码块原子 | 技术文档 |
| `semantic` | 句向量相邻距离找话题突变点，阈值取**分位数** | 无结构长文 |
| `hierarchical` | small-to-big：小块检索、父块喂模型 | 检索精度与上下文完整性都要 |

两个容易被忽略的细节：

- **标题路径下推**。每个块都带上 `H1 > H2 > H3`，检索命中孤立段落时模型仍知道它在讲什么——这是 chunk 脱离上下文这个经典问题最便宜的解法。
- **阈值用分位数而非绝对值**。不同文档的句间相似度基线差别很大，写死 `0.3` 换个语料就失效。

`chunk_stats()` 会输出块大小的**标准差**——方差大意味着检索打分失去可比性，这是评估切片质量最实用的单一指标。

### Token 预算：带优先级的资源分配，不是"塞满为止"

多数实现的做法是把历史全部拼接然后截断，后果是对话历史把工具定义挤掉、或者检索结果把用户问题本身挤掉。这里建模成**带下界、上界和优先级的分配问题**：

1. 按优先级逐个满足 `min_tokens` 保命线。预算不够时，优先级最低的分区**整块丢弃**——半截的工具定义比没有工具定义更糟。
2. 剩余预算按权重**注水（water-filling）**：吃饱的分区退出竞争，把余量还给池子，迭代到收敛。

```
[窗口 16384] 压力 1.4x   retrieved 9000→4303[压缩]  semantic 3000→3000[原样] ...
[窗口  8192] 压力 3.0x   scratchpad 2200→1546[压缩]  retrieved 9000→1360[压缩] ...
[窗口  2000] 压力 22.2x  tools/system/task 原样保留，其余六个分区全部丢弃
```

`system` / `task` / `tools` 标记为 `droppable=False`——它们是逐字原样输出的，所以保命线就是全部需求；真的塞不下时如实上报 `overflow`，而不是谎报"已压缩"。

### 压缩：四种手段，能不调模型就不调

`truncate`（兜底）→ `extractive`（查询感知抽取，**输出全是原文句子，不可能幻觉**）→ `middle_out`（针对 Lost-in-the-Middle，保头保尾压中间）→ `llm_summary`（map-reduce，压缩率最高但有成本和幻觉风险）。

选型原则：检索结果用抽取式，只有长对话历史才值得上 LLM 摘要。

### 组装：排布顺序对抗注意力衰减

顺序是 `system → 记忆/知识 → 历史 → scratchpad → 任务复述`。用户指令在开头出现一次、末尾再复述一次——两端是模型注意力最强的位置，中间放最能容忍被略读的背景材料。

每条注入内容都带 **provenance**（来源、分数、token 数），出问题时能回答"模型为什么会这么说"。

## 二、记忆系统 `keel/memory/`

四层划分来自认知心理学，但工程上分层的真正理由是**每层的读写时机和淘汰策略完全不同**：

| 层 | 内容 | 淘汰策略 |
|---|---|---|
| `working` | 当前会话近期轮次 | token 硬上限，溢出即滚动摘要 |
| `episodic` | 带时间戳的事件流 | 正常衰减 |
| `semantic` | 脱离时间的事实与文档块 | 衰减速度是情景记忆的 1/6 |
| `procedural` | 成功轨迹固化的技能 | 不遗忘，靠成功率淘汰 |

### 混合检索：四路信号融合

```
向量相似度  抗改写（"怎么切片" ↔ "分块策略"）
BM25       抗术语（ERR_7731、HierarchicalChunker 这类词向量常认不准）
时间新鲜度  艾宾浩斯衰减后的记忆强度
重要性     写入时的打分
```

前两路做混合召回（各自 min-max 归一化后加权，因为余弦 ∈[-1,1] 而 BM25 ∈[0,∞)），后两路做排序调权，最后 **MMR** 去冗余。检索接口会返回每一路的原始分数——检索效果没法调，往往就是因为看不到分解值。

### 遗忘曲线

```
strength = (importance/10) × exp(-Δt·ln2/半衰期) × (1 + 0.35·ln(1+被检索次数))
```

用 `last_access` 而非 `created_at` 计时：**每次被检索到 = 复习一次**，计时重置——这正是间隔重复的机制。强度跌破阈值的记忆被**归档而非删除**，不参与检索但仍可审计（遗忘策略几乎必然要调参，线上删数据是不可逆的）。

### 写入去重与反思固化

同一事实被反复说，应该是"加强"而不是"多存一份"：语义相似度超阈值则提升原记录重要性。文档入库同样幂等——重复上传不会让检索结果被同一段内容占满。

**反思固化**（Generative Agents 思路）：累积重要性超阈值时，让模型从一堆零散事件里抽出高层结论存进语义记忆，并保留 `derived_from` 指回来源。这让记忆不只是越堆越多，而是**会逐渐变得更抽象**。

## 三、Loop Engineering `keel/loop/`

Agent 跑飞的方式就那么几种，每种都要有对应的检测器和处置动作：

| 故障模式 | 检测方式 | 处置 |
|---|---|---|
| 预算超支 | 步数 / token / 成本 / 墙钟时间 | 硬停 |
| 原地打转 | 动作指纹重复计数 | 先反思，再犯则停 |
| 周期振荡 | 尾部序列找周期 `A-B-A-B` | 直接停（反思对它基本无效） |
| 进展停滞 | **信息增量**低于阈值 | 先逼它作答，再犯则停 |
| 下游故障 | 工具熔断器 | 拒绝调用，不再烧 token |

四个关键设计：

**1. 动作指纹必须参数无关。** `{"a":1,"b":2}` 和 `{"b":2,"a":1}` 要同指纹，否则死循环检测直接失效。

**2. 进展用"信息增量"而不是"动作有没有变"。** 换个措辞搜同一个东西，动作不同但信息为零。这里把新观察和历史观察都转成向量，取 `1 - max相似度` 作为新颖度。

**3. 优先降级而不是报错退出。** 先给一次自我纠正的机会（反思），不行就强制它用现有信息作答，最后才放弃。用户拿到"基于已知信息的部分答案 + 明确的未完成说明"，永远好过拿到一个超时错误。

**4. 反思结论要有代码层的约束力。** 只把"别再这么做"写进 prompt，模型经常照做不误；这里把失效动作写入 `avoid_actions` 黑名单，引擎在**执行前**拦截。

```
[第 3 步] reflect  检测到动作重复 3 次, 触发反思重规划
[第 4 步] stop     同一动作已重复 4 次, 反思未能纠正
终止: loop_detected | 步数 4 (上限 12) | 即便被中止仍产出降级答案
```

> 踩过的坑：重复计数是单调递增的，反思一结束护栏会立刻再次触发，变成"反思死循环"。所以 `LoopPolicy` 要记住已经为哪些指纹反思过。
>
> 另一个坑：scratchpad 是可压缩分区，压缩会把"我做过什么"吃掉，模型于是重复调同一个工具。解法是把**已执行动作清单注入系统提示词**（不可丢弃分区），保证 100% 存活。

## 四、多 Agent 编排 `keel/orchestrator/`

**为什么用 DAG 而不是 Supervisor 动态派发**：Supervisor 每派一次任务都要过一遍模型，决策成本高且天然串行；DAG 把规划和执行分开，同一层的节点可以真并发。代价是执行中途改不了图——所以用 Critic 兜底，产出不合格就带着意见重新汇总。

```
第 1 层(并发): t1 查发布规定 | t2 搜 ReAct 论文 | t3 计算 (99+1)*3
第 2 层:       t4 汇总（依赖 t1,t2,t3）
并发收益: 串行需 1815ms, 实际 1114ms, 加速 1.63×
```

三个工程判断：

- **单节点直跑**。编排本身有成本（多一次规划 + 一次汇总的模型调用），规划出来只有一个节点时自动降级为 ReAct 直跑。[消融数据](#消融实验这些护栏到底有没有用)显示这个阈值其实该再往上调——小任务编排是净亏损。
- **规划器产出非法图是常态不是异常**。指向不存在节点的依赖直接剪掉，有环则降级成全并行，绝不让整轮失败。
- **上游失败则下游跳过**。拿着残缺输入硬跑只会产出垃圾并浪费预算。
- **质检只重跑汇总，不重跑执行**。多数质量问题出在整合环节而非取证环节。

## 五、可观测性与 Web 控制台

Agent 是非确定性系统，"能复现"比"有日志"重要得多。`Tracer` 是 OpenTelemetry 的极简同构版：Span 树 + `contextvar` 隐式父子关系，额外把 token/成本沿树汇总——一眼看出钱花在哪个环节。

> 并发编排时多个 Task 共用一个 Tracer，span 栈必须放在 `contextvar` 里；放在实例上的话各任务的 push/pop 会交错，父子关系全乱。

控制台六个页签（`http://127.0.0.1:8000`）：

- **对话 / 执行** — SSE 逐步推送思考、工具调用、护栏触发、反思；实时显示上下文分区占用
- **调用链追踪** — Span 树、每个环节的 token 与耗时
- **记忆浏览器** — 四层记忆、强度、命中次数；可手动触发遗忘与反思固化
- **上下文实验室** — 把窗口调到 1500 就能直接看到低优先级分区被丢弃、高优先级被压缩，以及最终送进模型的完整消息
- **切片实验室** — 五种策略并排对比块数、token 分布、标准差
- **消融实验** — 界面上直接跑 A/B，实时看命令行输出；历次结果留档，画出每个指标随 commit 的走向。绿点表示比上次更好、红点更差——"这次改动让哪个指标变差了"从此是个能当场回答的问题

前端是 React + TypeScript（Vite 构建），源码在 `web/`。这里 TypeScript 挣的不是"少写几个 bug"，而是**把前后端契约钉死**：`web/src/types.ts` 里那个 `ChatEvent` 联合类型枚举了服务端会推的全部 20 种 SSE 事件，服务端新 emit 一种却忘了在前端登记，`tsc` 会当场报错，而不是让这个事件在页面上静默消失。趋势图是手写的内联 SVG，没引图表库——要画的只是折线，为此拖进来一个 200KB 的依赖不划算。

## 六、工程实践

**测试**：114 个用例全部跑在 Mock Provider 上——无需 API Key、完全确定性、CI 零成本。这是 Provider 抽象带来的直接收益。覆盖切片 token 边界、预算优先级丢弃与溢出上报、遗忘曲线半衰期、去重、BM25 精确召回、MMR 多样性、动作指纹、周期检测、熔断三态、DAG 环检测与失败传播、并发隔离。`conftest` 显式把全局 Provider 与 MemoryManager 钉在 Mock 上——测试的确定性不该取决于本地 `.env` 里配了什么。

**安全边界**：`calculator` 用 AST 白名单而非 `eval`；`python_exec` 禁掉 import / 属性访问 / `while True`；`read_file` 解析绝对路径后校验是否越出 data 目录。这些都是被 prompt injection 打过之后的标准做法。

**容错**：工具异常一律转成可读的 observation 回灌给模型（"缺少必填参数 expression"，模型下一轮基本能自己改对），而不是抛异常中断循环；记忆写回失败不影响主流程。

**降级要出声**：embedding 服务挂了会降级到本地 hashing 向量，但降级**latch 一次就不再重试**（DeepSeek 没有 `/embeddings`，否则每次调用都要白烧 3 次 HTTP 重试 + 指数退避）、打一条 stderr 告警、并把 `degraded` 写进 trace 属性。静默降级是最坏的一种容错：hashing 向量不懂近义词，而且维度一旦和库里已有向量不一致，`cosine()` 长度不等时会直接返回 `0.0` 而不报错——向量通道整条失效、检索悄悄退化成纯 BM25，全程零异常。

## 七、把评测接进 CI

单元测试守的是"功能没坏"，但 Agent 系统的退化往往不抛异常——它只是悄悄多烧了 30% 的 token、多绕了两步。没有基线对比的话，这类退化不会被任何断言抓到。所以这里把消融实验也接进了 CI：

| 工作流 | 触发 | 做什么 |
|---|---|---|
| `ci.yml` | push / PR | 114 个测试跑 Python 3.10/3.11/3.12 矩阵；起服务跑 38 项 HTTP/SSE 冒烟；`demo.py all` 串一遍五个场景；前端类型检查、重新构建并校验产物未陈旧 |
| `bench.yml` | PR | 在**同一台 runner** 上分别跑基线分支和 PR 的实验，逐项对比 39 个指标，把结果贴成 PR 评论；有退化则 CI 失败 |
| `pages.yml` | push 到 main | 重跑实验、渲染报告、发布到 GitHub Pages |

几个值得说的判断：

**基线现跑，不读存档。** 墙钟类指标受机器规格影响，跨机器对比会把硬件差异误判成代码退化。所以基线分支在同一个 runner 上现场跑一遍，多花 30 秒换来可比性。

**指标自带方向。** 每个指标在产出时就写好了 `lower` / `higher` / `info`，而不是把方向写死在比对脚本里。这样历史产物是自解释的——半年后指标定义变了，旧产物也不会被反向解读。`info` 类（墙钟耗时等）只展示不判定，因为它们受 CI 负载影响，拿来卡门槛只会制造噪声。

**基线为 0 的指标不看相对变化。** 0 → 3 的相对变化是无穷大，报出来只会淹没真正的信号，所以这类指标退回看绝对量。

**首次接入不能硬失败。** 基线分支上还没有产物是正常的，比对脚本识别到产物缺失就输出"跳过对比"，否则第一个 PR 永远合不进去。

**前端产物提交进仓库，就必须有人守着它别过期。** 把构建产物纳入版本控制是为了让 clone 下来 `pip install` 就能起服务——看项目的人不该为了打开界面先装一套 Node 工具链。代价是产物会和源码脱节：改了 `web/` 却忘了构建，仓库里的界面就是旧的，而且没有任何报错。所以 CI 重新构建一遍再比对 `git status`，不一致就失败。为此还要把 `keel/server/static/**` 在 `.gitattributes` 里标成 `-text`：本机在 Windows 构建、CI 在 Linux 重建，中间只要有一次 CRLF 转换，字节比对就会误报。

CI 全程跑在离线 Mock 上——零 API Key、零成本、完全确定性。换成真模型的话断言结果会取决于当天模型的心情，CI 就只能沦为摆设。

## 部署

```bash
docker compose up --build          # 本地容器，http://127.0.0.1:8000
fly deploy                         # 公网（fly.toml 已配好缩容到零）
```

**公网模式的自我保护**（`KEEL_PUBLIC_MODE=true`）：把控制台挂到公网等于开放一个任何人都能触发的 CPU 入口——一次编排请求要跑十几次模型调用，切片实验室能吃下任意大的文档。所以公网模式下按 IP 滑动窗口限流（只限贵的那些端点，健康检查和记忆浏览不限，否则界面自身的轮询会把配额吃光）、输入长度设上限、消融实验触发直接关闭。本地开发默认全关——实验室就是用来喂大文档的。

限流器是进程内的，多副本部署时各算各的。要精确就得引入 Redis，为一个零外部依赖的 demo 挂状态存储不划算——这是个取舍，不是疏漏。

## 已知取舍

诚实说明当前实现的边界，以及生产化需要补的部分：

| 当前 | 生产化方向 |
|---|---|
| 离线用 hashing embedding（feature hashing，只能捕捉字面重合），会系统性低估 MMR 消融的收益 | 换真 embedding 模型（如通义 `text-embedding-v3`），检索层代码零改动 |
| 记忆存在进程内存 | `MemoryStore` 接口按可替换成 pgvector / Milvus 的形状设计——但**没被真正替换过**，接口的可替换性目前只是设计意图 |
| 病态任务（死循环 / 周期振荡）的量化依赖 Mock 的确定性触发词，真实模型下无法复现同一条曲线 | 用故障注入的假工具制造真实模型也会踩的陷阱 |
| 评测集是自建的 12 个任务 + 5 组机制消融，规模小、判分是关键词匹配 | 规模化后接 LLM-as-judge；但要先解决 judge 自身的方差 |
| `python_exec` 用线程 + AST 白名单，超时无法真正杀死线程 | 子进程 + cgroup 资源限制 |
| 重要性判定是启发式规则 | 小模型打分；但规则的零延迟和可解释性在冷启动阶段更实用 |
| 无 token 级流式（只流式推送步骤事件） | 接 provider 的 stream 接口 |
| Trace 存在内存环形缓冲 | 导出到 OTLP / Langfuse |
